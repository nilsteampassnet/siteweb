The problem

Passkeys were built for one person. Teams share accounts.

A passkey replaces a password with a key held by a device or by a personal password manager. That suits an account one person owns. It suits the supplier portal, the registrar or the social media account that four colleagues use much less well.

{% include components/icon.html name="users" %}

A shared account on one person's device

The passkey of a shared account ends up on the phone, or in the personal manager, of whoever created it. Their holiday, or their departure, becomes everyone's problem.

{% include components/icon.html name="key" %}

So shared accounts stay on passwords

Rather than depend on one colleague, the team declines the passkey the site offers and keeps the password in the vault, where everyone who needs it can reach it.

{% include components/icon.html name="lock" %}

And the vault still opens with a password

The place that holds every credential is itself protected by what passkeys were meant to replace: something typed, which can be typed into the wrong page.

Two features, two switches

For the sites your team uses, and for Teampass itself

Teampass uses passkeys for two independent things, each with its own settings. Both are off until an administrator turns them on.

{% include components/icon.html name="key" %}

Passkeys of other sites

Teampass keeps the passkeys of third-party sites in its items, like it keeps their passwords, and the browser extension signs in with them. The server side is open-source; the extension is the paid add-on.

How it works {% include components/icon.html name="arrow-right" %}
{% include components/icon.html name="user-check" %}

Signing in to Teampass

A passkey confirms, or replaces, the password of a Teampass account. It needs the open-source server, HTTPS and a browser that supports passkeys — no extension.

How it works {% include components/icon.html name="arrow-right" %}
{% include components/icon.html name="info" %}

Turning one on does not turn the other on, and a passkey of one is never usable by the other.

Passkeys of other sites

The private key is created, kept and used on your server

A passkey kept in Teampass is not a file handed to each browser. The extension relays the request of the site; the server signs it and sends back the signature, nothing else.

  1. Step 1

    A site offers a passkey

    A Teampass window opens in the browser. Choose the item to store the passkey in, or create a new one in a folder of your choice, then save.

  2. Step 2

    The server generates the key

    An ECDSA P-256 key pair is generated on the Teampass server. Its private key is encrypted with a key of its own, itself encrypted for each user — the same scheme as item passwords.

  3. Step 3

    The site asks for it later

    Choose the account and sign in. The extension relays the request, the server signs it for the site the passkey was created for, and only the signature comes back.

  4. Step 4

    The use is recorded

    Passkey added, Passkey used and Passkey deleted are written to the item history with the site concerned, under the user the server signed for.

{% include components/icon.html name="users" %}

Everyone who can open an item can use its passkeys. A passkey saved in a shared folder signs in for every member of that folder, exactly like its password. One saved in a personal folder signs in for its owner only.

A passkey saved without your knowledge gets noticed. The user who saves a passkey is e-mailed the site, the account and the item, unless the administrator turns the notification off. A passkey added with a stolen session does not stay silent.

Signing in to Teampass

A second factor, or no password at all

A fingerprint, a face, a PIN or a security key confirms a Teampass sign-in instead of a code, and can replace the password entirely. The passkey is registered by the user and never leaves their device: Teampass only stores its public key.

{% include components/icon.html name="shield-check" %}

As a second factor

After the login and the password, Teampass asks for the passkey. Where Google Authenticator or Duo is already required, the passkey is offered next to them and the user picks one.

{% include components/icon.html name="zap" %}

Without a password

In passwordless mode, the login page shows Sign in with a passkey. The account is the one the chosen passkey belongs to: nothing has to be typed, and one click opens the browser dialog.

{% include components/icon.html name="user-check" %}

Offered, never imposed

An account without a passkey signs in exactly as before. There is no enrolment during sign-in: users add up to 20 passkeys from their profile, after confirming their password.

{% include components/icon.html name="activity" %}

Adoption you can see

A badge on the Users page gives the number of sign-in passkeys of each account, and the administration dashboard counts the active accounts that hold one.

A lost authenticator never locks anyone out for good. An administrator, or a manager of the account, revokes the passkey from the Users page, and the account goes back to its password, plus any other method it had.

Guard rails

What the server refuses to do

Each rule below is enforced by the server, whatever the extension or the browser asks for.

{% include components/icon.html name="lock" %}

No endpoint returns the private key

The API signs on the server and sends back the signature only. The credential identifier is random and generated by Teampass, never supplied by the client.

{% include components/icon.html name="shield-check" %}

Bound to its site

A passkey signs only for the site it was created for. A signature counter grows at each use, which lets a site detect a cloned passkey.

{% include components/icon.html name="x-circle" %}

The vault's own passkey stays out of the vault

The server refuses to keep the passkey of its own sign-in page in an item: it would let everyone who can open that item sign in as its owner.

{% include components/icon.html name="user-check" %}

A password before a new passkey

An open session is not enough to add a sign-in passkey. Whoever finds one unattended cannot register a passkey of their own and keep signing in after the owner changed their password.

{% include components/icon.html name="layers" %}

An encryption key that stays wrapped

A passwordless passkey carries an encrypted copy of the user's encryption key, opened by a secret only the authenticator can produce or, without PRF, by a key derived from the instance secret file. A setting refuses the second.

{% include components/icon.html name="activity" %}

Refusals count, changes are logged

A refused passkey counts towards the account lockout like a wrong password. Additions, deletions and passwordless changes are logged, and the owner is e-mailed when a passkey is added.

Administrator policy

Off by default, and yours to scope

The first setting is under Settings → API → Browser Extension, the others under Settings → MFA → Passkeys; the notification is on both tabs. The names below are the ones the settings pages show.

Choose the relying party ID before users register. Authenticators bind a passkey to that domain: changing it makes every registered sign-in passkey unusable. When passkeys exist, Teampass asks for a confirmation before saving a new value.

For the passkeys of other sites, the API rights of each user decide what the extension may do on their behalf: Read to sign in, Update to save or delete a passkey — on top of the right to edit the item, never beyond it.

Honest scope

What passkeys in Teampass do not do

{% include components/icon.html name="minus-circle" %}

Work without the server

The private key never leaves the server: a passkey kept in Teampass cannot be used while the server is down or unreachable, and it is not part of the offline export. Keep another way to sign in on every account it protects.

{% include components/icon.html name="minus-circle" %}

Import, export or survive an old backup

Passkeys stored elsewhere cannot be imported, and those kept in Teampass cannot be exported. Restoring a backup loses the passkeys saved since that backup, while the sites still expect them.

{% include components/icon.html name="minus-circle" %}

Satisfy every site

Sites that require attestation or device-bound passkeys, as some enterprise identity providers do, do not accept Teampass passkeys. Only ES256 passkeys are created, and the extension does not offer passkeys in the browser's autofill suggestions, nor inside frames.

{% include components/icon.html name="minus-circle" %}

Replace the directory password

LDAP and OAuth2 accounts use their passkey as a second factor only. An instance whose accounts all come from a directory gains nothing from the passwordless mode.

Getting started

From switched off to a first passkey

  1. Serve Teampass over HTTPS

    Browsers only offer passkeys in a secure context. For the passkeys of other sites, also enable Require HTTPS for API requests: System Health warns while the API still accepts plain HTTP.

  2. Turn on what you need

    Allow the browser extension to save passkeys in Settings → API → Browser Extension, a mode for Sign in with a passkey in Settings → MFA → Passkeys, or both.

  3. Save the first one

    With the extension, accept the passkey a site offers and store it in an item. For Teampass itself, add one from Profile → Sign-in and security → Sign-in passkeys.

{% include components/icon.html name="book" %}

Both features arrived in 3.2.3.0 — see What's new. The passkeys of other sites need the browser extension 1.8.0 or later. Every setting, restriction and error message is described in the Passkeys documentation.
