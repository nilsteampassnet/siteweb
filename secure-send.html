The problem

Every team sends passwords to outsiders. Usually by e-mail.

A supplier needs the router password, an auditor needs a read-only login, a freelancer needs the staging credentials for a week. The vault cannot reach them, so the password leaves it the quickest way available — and stays wherever it landed.

{% include components/icon.html name="mail" %}

A sent password never leaves

It stays in both mailboxes, in the backups of both mail servers and in every search index along the way, long after the work it was sent for is finished.

{% include components/icon.html name="users" %}

An account is too much for one password

Creating a vault account for an outsider means standing access, folder rights to get right, and an offboarding step that someone has to remember once the job is done.

{% include components/icon.html name="search" %}

Scanners open one-time links first

Mail security gateways and chat previews follow links as soon as they arrive. A link that reveals its content on first opening is consumed before the person it was meant for ever sees it.

How a link works

Nothing is revealed until the recipient asks for it

A Secure Send link is not a page that displays a password. It is a request the recipient has to confirm, checked against every limit at the moment they do.

  1. Step 1

    Choose what to share

    From the item, set how many days the link lives and how many views it allows, within the limits your administrator set. Add a passphrase, and the current TOTP code if the recipient needs it.

  2. Step 2

    Send the link

    Copy the link and send it as usual. Send the passphrase through a different channel — a phone call, a chat — so that intercepting one message is not enough.

  3. Step 3

    The recipient confirms

    Opening the link shows the expiry date, the remaining views and, when configured, the sender's organisation. Nothing is decrypted and nothing is counted until the recipient confirms.

  4. Step 4

    Revealed, counted, gone

    The view is reserved before the content is shown. When the last view is used or the expiry date passes, the link stops working for good.

{% include components/icon.html name="user-check" %}

The sender's access is checked again at every opening. A link created by someone who has since been disabled, or who lost access to the item, stops working — even if it has not expired yet. Deleting the item stops its links too.

Guard rails

A link to a password has to fail closed

Every limit is enforced by the server, at the moment the link is used — not by the page, and not only when the link is created.

{% include components/icon.html name="shield-check" %}

Confirmation before reveal

Only an explicit confirmation reveals the content and uses a view. Link previews and scanners open the page and consume nothing.

{% include components/icon.html name="activity" %}

Limits that hold under load

Views and failed attempts are reserved in a single database transaction, so concurrent requests cannot exceed a link's limits. Five wrong attempts revoke it.

{% include components/icon.html name="user-check" %}

Access checked at every opening

The sender's current right to the item is verified when the link is created, again before anything is decrypted for the recipient, and when the sender lists their links.

{% include components/icon.html name="layers" %}

A copy, frozen at creation

The link carries an encrypted copy of the item as it was. A description too long for it is shortened and both sides are told; the credentials themselves are never cut.

{% include components/icon.html name="clock" %}

TOTP codes, never the seed

When the sender chooses to share it, the recipient gets server-generated codes. The TOTP secret is never sent to a browser.

{% include components/icon.html name="lock" %}

Nothing for the browser to keep

The recipient page forbids caching, framing and referrers, and runs under a restrictive Content Security Policy.

Publishing links

Reachable from the Internet, with the vault still private

Recipients are outside your network, your vault should not be. A public sharing address puts the recipient page on a dedicated hostname, and the sender picks it link by link — the internal address stays the default, and the dialog always shows which one a link will use.

Honest scope

What a Secure Send link does not carry

{% include components/icon.html name="minus-circle" %}

Custom fields, tags and attachments

The shared copy holds the label, login, URL, description and password, plus the TOTP code when the sender chooses to include it. Files and custom fields stay in the vault.

{% include components/icon.html name="minus-circle" %}

Ongoing access

A link is for handing over a credential once, or a few times. Someone who needs the item for months belongs in Teampass, with an account and folder rights you can review.

Getting started

From switched off to a first link

  1. Set the policy

    In Settings → Options → Collaboration, turn on User can propose One-Time-View links, then set the longest validity, the view limit and whether a passphrase is mandatory.

  2. Decide where links point

    Internal recipients only? Nothing more to do. Outsiders? Declare a public sharing address and publish it by following the deployment guide, then set your organisation name.

  3. Send the first one

    Open an item, choose Secure Send, generate the link and copy it. Send the passphrase separately, and watch the link in My secure sends.
